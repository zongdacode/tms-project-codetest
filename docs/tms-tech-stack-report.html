🏗️ TMS 技术选型评估报告

单体起步 → 粗粒度服务演进（3-5 个大服务，非细粒度微服务）

🎯一、核心结论（先看这个）

推荐方案：Spring Boot 模块化单体起步，未来按需拆成 3-5 个粗粒度服务

1.1 你的架构思路（我理解的）

  • 起步阶段 — 单体应用，4-5 家工厂用，够用就行
  • 未来演进 — 不是拆成几十个细粒度微服务，而是拆成 3-5 个大服务
  • 服务粒度 — 按业务大模块拆：权限、基础数据、TMS、WMS、结算…
  • 权限统一 — 统一认证、统一权限管理，各服务共用一套用户体系
  • 基础数据 — 可以独立成服务，也可以挂在某个核心服务下（灵活处理）
✅ 这个思路非常务实！这叫「粗粒度服务化」，比纯单体好扩展，比细粒度微服务运维简单得多，最适合中大型业务系统。

1.2 一句话技术选型

维度选择理由
后端框架 Spring Boot 3.3.x Java 生态事实标准，升级 Spring Cloud 最顺
架构模式 模块化单体 → 粗粒度服务 起步简单，后期按需拆分，不追求细粒度
ORM MyBatis-Plus 3.5.x TMS/WMS 复杂查询多，SQL 灵活度要求高
数据库 MySQL 8.4（单库 → 按服务分库） 起步单库，未来每个服务一个库
服务框架（未来） Spring Cloud Alibaba 服务数量少，用最轻量的配置即可
服务通信（未来） OpenFeign（HTTP） 3-5 个服务，HTTP 足够，调试方便
统一认证 OAuth2 / JWT + 统一用户中心 各服务共享一套用户权限体系

🤔二、为什么选「粗粒度服务」而不是「细粒度微服务」？

🎯 你的方案：粗粒度服务（3-5个）

优势：

  • 运维复杂度可控 — 3-5 个服务，几个人就能管
  • 分布式事务少 — 核心业务在一个服务内，事务简单
  • 服务间调用少 — 链路短，排查问题容易
  • 团队不用太大 — 每个服务 1-2 人就能维护
  • 性能损耗小 — 跨服务调用少，网络开销低

不足：

  • 服务内代码量可能还是不小
  • 扩缩容粒度还是偏粗

⚠️ 不推荐：细粒度微服务（10+个）

理论优势：

  • 每个服务很小，独立部署扩展
  • 团队可高度并行开发
  • 故障隔离更彻底

实际问题：

  • 运维成本爆炸 — 需要专业 DevOps 团队
  • 分布式事务是噩梦 — 一个业务流程跨 N 个服务
  • 链路追踪复杂 — 排查问题像破案
  • 团队要求高 — 小团队根本扛不住
  • 大部分公司最后都拆太细了，反而合并回来
⚠️ 行业共识：微服务拆分越细，复杂度越高。很多公司最后发现「拆得越细，死得越快」。对于 4-5 家工厂规模的 TMS 系统，3-5 个粗粒度服务是性价比最高的选择。

🧩三、服务拆分方案（未来演进目标）

3.1 推荐拆法：5 个服务

🔐 统一认证服务
用户、角色、权限
登录认证、Token 管理
📦 基础数据服务
工厂、客户、供应商
地点、车辆、司机、商品
🚚 TMS 运输服务
订单、调度、运输跟踪
运费核算、报表
🏭 WMS 仓储服务
入库、出库、库存
盘点、库位管理
💰 结算服务
应收应付、账单
对账、发票、核销

3.2 各服务职责说明

服务 核心模块 数据独立性 拆分时机
🔐 统一认证服务 用户管理、角色权限、菜单管理、登录认证、Token 管理、操作日志 独立用户库，所有服务共用 第 2 阶段就拆
📦 基础数据服务 工厂/仓库、客户、供应商、地点、车辆、司机、商品、字典 独立基础数据库，各业务服务调用 第 2 阶段可拆
🚚 TMS 运输服务 运输订单、调度派车、在途跟踪、签收、运费、TMS 报表 独立 TMS 业务库 核心，单体时就在
🏭 WMS 仓储服务 入库、出库、移库、盘点、库存、库位、条码 独立 WMS 业务库 WMS 上线时拆
💰 结算服务 应收/应付、账单生成、对账、发票、核销、财务报表 独立结算库 业务稳定后拆

3.3 备选方案：4 个服务（基础数据挂在 TMS 下）

如果你觉得基础数据单独拆一个服务太轻量，可以把基础数据挂在 TMS 服务下：

  • 统一认证服务（独立）
  • TMS 服务（含基础数据）
  • WMS 服务
  • 结算服务
建议：起步阶段基础数据就在单体内，等拆服务时再决定是否独立。代码里先把基础数据模块独立出来，以后搬不搬都灵活。

🗺️四、架构演进路线图

阶段 1 · 当前

🏠 模块化单体（MVP 阶段，4-5 家工厂）

部署形态：一个 Spring Boot 应用 + 一个 MySQL 数据库

代码结构：按业务域严格分模块，模块间通过 Service 接口调用

数据库：单库，表按模块加前缀（sys_、base_、tms_、wms_、fee_）

多工厂：通过 tenant_id 数据隔离

目标：快速跑通 TMS 核心业务，验证产品

时间 第 1-3 个月

阶段 2

🔐 拆出统一认证服务（第一个服务）

为什么先拆这个：

  • 认证是所有系统的共用基础，先拆出来最合理
  • 认证服务逻辑简单、边界清晰，最容易拆
  • 以后上 WMS、结算等新系统，直接对接统一认证

改动内容：

  • 把用户/角色/权限/登录模块独立成认证服务
  • 引入 Nacos 做注册中心 + 配置中心
  • 引入 API 网关（Spring Cloud Gateway）
  • 业务系统通过 Token 调用认证服务校验权限

部署形态：2 个应用（认证服务 + 业务单体）+ 2 个数据库

时间 第 4-6 个月（业务稳定后）

阶段 3

🏭 WMS 独立成服务（第二个服务）

为什么拆 WMS：

  • WMS 业务独立性强，和 TMS 是松耦合关系
  • WMS 可能和 TMS 不是同时上线，可以独立开发部署
  • WMS 有自己的一套实体和流程，边界清晰

改动内容：

  • WMS 模块独立成服务，有自己的数据库
  • TMS 和 WMS 通过 OpenFeign 互相调用（比如 TMS 查库存）
  • 基础数据（商品、仓库、客户等）的归属需要明确

部署形态：3 个应用（认证 + TMS + WMS）+ 3 个数据库

时间 WMS 模块上线时

阶段 4

💰 结算服务独立（第三个服务）

为什么拆结算：

  • 结算是财务相关，数据敏感，独立性高
  • 结算逻辑复杂，单独一个服务更利于维护
  • 未来可能对接财务系统（用友、金蝶），独立更方便

部署形态：4 个应用（认证 + TMS + WMS + 结算）+ 4 个数据库

时间 结算模块上线且业务稳定后

阶段 5 · 可选

📦 基础数据服务独立（可选）

什么时候考虑拆：

  • 多个业务服务都频繁调用基础数据，成为瓶颈
  • 基础数据需要单独的权限和管理流程
  • 有其他系统（比如 CRM、OA）也需要用这些基础数据

部署形态：5 个服务 + 5 个数据库

时间 看实际需要，不一定要拆

🎯 演进原则：能不拆就不拆，需要了再拆。每拆一个服务，都是因为实际遇到了问题（团队协作、性能瓶颈、独立部署需求），而不是为了"看起来先进"。

5.2 模块间调用规则（最重要！）

⚠️ 这是未来能不能顺利拆服务的关键，从第一天起就要严格执行：
  1. 只能调用其他模块的 Service 接口，不能直接调用 Mapper 或访问数据库
  2. 每个模块有自己的 Service 接口层，其他模块只能依赖接口，不能依赖实现类
  3. 跨模块不能直接操作对方的数据库表，必须通过对方的 Service
  4. 跨模块的数据传输用 DTO，不能直接传 Entity（数据库实体）
  5. 每个模块的表加前缀（sys_、base_、tms_、wms_、fee_），一眼就知道属于哪个模块

5.3 跨模块调用示例

// ✅ 正确：调用基础数据模块的 Service 接口
@Service
public class TmsOrderServiceImpl implements TmsOrderService {

    @Autowired
    private BaseCustomerService baseCustomerService;  // 依赖接口

    public void createOrder(TmsOrder order) {
        // 通过接口获取客户信息，不直接查 base_customer 表
        BaseCustomerDTO customer = baseCustomerService.getById(order.getCustomerId());
        // ...
    }
}

// ❌ 错误：直接操作其他模块的表
@Service
public class TmsOrderServiceImpl {
    @Autowired
    private BaseCustomerMapper baseCustomerMapper;  // 直接注入别的模块的 Mapper
    
    public void createOrder(TmsOrder order) {
        BaseCustomer customer = baseCustomerMapper.selectById(order.getCustomerId());
        // 这样写，以后拆服务就痛苦了！
    }
}

模块表前缀示例

7.2 必含字段（每张表都要有）

  • id — 主键，用雪花算法 ID（不是自增，方便分库）
  • tenant_id — 工厂/租户 ID，多工厂数据隔离用
  • create_by — 创建人
  • create_time — 创建时间
  • update_by — 更新人
  • update_time — 更新时间
  • deleted — 逻辑删除标记（0 未删除，1 已删除）
💡 为什么用雪花 ID 不是自增 ID：未来分库后，自增 ID 会冲突。雪花算法生成的全局唯一 ID，拆库的时候不用改主键策略。

7.3 分库策略（未来）

拆服务时，直接按模块把表分到不同的数据库即可：

  • auth_db → 所有 sys_ 开头的表
  • base_db → 所有 base_ 开头的表（如果独立的话）
  • tms_db → 所有 tms_ 开头的表
  • wms_db → 所有 wms_ 开头的表
  • fee_db → 所有 fee_ 开头的表

⚠️八、主要风险与应对建议

风险点 影响 应对策略
单体阶段代码写乱了，模块边界模糊 高 从第一天起严格执行模块调用规则，代码 review 重点查跨模块调用
跨服务调用太多，性能受影响 中 服务不要拆太细（3-5个足够），必要的数据冗余，加缓存
分布式事务处理复杂 中 尽量把强关联的业务放在同一个服务里；必须跨服务的，用最终一致性 + 补偿机制
Nacos/Gateway 等中间件运维复杂 低 3-5 个服务量不大，单机部署 Nacos 即可，不用搞集群
团队技术能力跟不上 中 不急着拆，单体能用就用。拆一个服务就要吃透一个，不追求一步到位

给你的 5 条建议

  1. 先跑起来，再优化 — MVP 阶段速度最重要，别纠结完美架构
  2. 模块边界从第一天就要守住 — 这是未来能不能顺利拆服务的关键
  3. 服务拆到 3-5 个就够了 — 别追求"微"，粒度太细反而是灾难
  4. 认证服务第一个拆 — 边界最清晰，价值最大
  5. 能不拆就不拆 — 每个拆分决策都要有实际理由，而不是"为了先进"

📌九、最终总结

✅ 推荐架构

单体起步 → 按业务大模块逐步拆分成 3-5 个粗粒度服务

技术栈：Spring Boot 3 + MyBatis-Plus + MySQL 8.4 + Redis + Vue 3 + Element Plus

未来服务化：Spring Cloud Alibaba（Nacos + Gateway + OpenFeign）

演进节奏

阶段 1: 【单体应用】 → 所有模块在一起
1 个应用 + 1 个库
阶段 2: 认证服务 + 业务单体 → 2 个应用 + 2 个库
阶段 3: 认证 + TMS + WMS → 3 个应用 + 3 个库
阶段 4: 认证 + TMS + WMS + 结算 → 4 个应用 + 4 个库
🎯 核心理念： 简单起步，逐步演进。用单体的速度开发，用服务化的思维组织代码。需要多少拆多少，不盲目追求技术先进。
