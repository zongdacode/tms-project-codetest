## 1. 架构总览

**Spring Boot 模块化单体（1 应用 + 1 库）起步，代码按"未来服务"边界组织；能不拆就不拆，拆只拆粗粒度。**

技术栈（报告第六章，版本修正见 §8-A1）：

| 层 | 选型 |
|---|---|
| 后端 | JDK 21 LTS + **Spring Boot 4.1.1**（Gate 0 已过，见 [13](13-gate0-技术栈验证报告.md)）+ MyBatis-Plus **3.5.17**（boot4 starter）+ Spring Security/JWT + SpringDoc **3.1.1** |
| 数据 | MySQL 8.4：单库分表前缀 → 拆服务时按前缀分库 + Redis 7.x（缓存/Token/分布式锁）+ 对象存储（附件/回单） |
| 服务化（阶段 2 触发） | Spring Cloud Alibaba：Nacos + Gateway + OpenFeign；Seata 仅确有必要时 |
| 前端 | Vue 3 + TypeScript 5 + Element Plus + Vite + Pinia + Vue Router + Axios |

```
            Web 前端 (tms-web)
                 │ HTTPS
       [ tms-admin 单体应用 ] ◄── 外部系统对接（随 TMS 业务范围确定）
                 ▼
 tms-auth │ tms-base │ tms-plan │ tms-core（核心）
   模块间只走对方 api 接口，禁止跨模块查表
                 ▼
  MySQL 单库（sys_/base_/tms_ 前缀） + Redis + 对象存储
```

演进节奏（报告第四章，TMS 起步下对阶段 1 做范围收紧）：

| 阶段 | 形态 | 触发 |
|---|---|---|
| 1（当前） | 单体：auth+base+tms 实装；tenant_id 多工厂隔离 | 第 1–3 个月 |
| 2 | 拆统一认证服务，引入 Nacos/Gateway/Feign/Docker | 业务稳定（第 4–6 月） |
| 3（可选） | 基础数据独立 | 多服务频繁调用成瓶颈时 |

## 2. 后端 Maven 模块拆分（报告 5.1 骨架 + 两处微调）

```
tms-project/                        # 根 pom（groupId/包名 com.xxx.tms，立项定）
├── tms-common/                     # 【无表】工具类、统一响应 Result、异常码、注解、UserContext
├── tms-framework/                  # 【微调新增，见 A-2】自动装配组件，被各业务模块依赖
│   ├── mybatis/                    #   MP 配置：分页/乐观锁/逻辑删除/审计字段自动填充/号段ID
│   │   └── tenant/                 #   tenant_id 行级拦截器——多工厂隔离框架层强制，不靠自觉
│   ├── security/                   #   JWT 解析、登录上下文、权限注解校验
│   ├── redis/                      #   缓存封装、分布式锁
│   ├── file/                       #   对象存储 + sys_attachment 附件元数据服务（02 AI-ready 原则3）
│   └── event/                      #   单据事件发布 → tms_event 时间线表（02 AI-ready 原则1）
│
├── tms-auth/                       # 【未来服务①】sys_ 表：用户、角色、菜单、登录、Token、操作日志
│   ├── api/  controller/  service/impl/  mapper/  entity/  dto/  config/
│
├── tms-base/                       # 【未来服务⑤·可选】base_ 表：工厂、客户、供应商(承运商)、
│   └── ...                         #   地点、车辆、司机、商品、字典、地址（省市区码+经纬度，02 原则2）
│
├── tms-plan/                       # 【核心服务③之一】tms_order_plan：上游计划落地 + 节点状态回填，
│   └── api/ mapper/ entity/        #   只维护 [05-data-model] §2 的 26 列白名单（红线 R-2，见 §8-A8）
│
├── tms-core/                       # 【核心服务③·永不先拆】tms_ 表——按报告 3.2 职责组织子域：
│   ├── api/                        #   对外唯一入口（接口+DTO，见 A-3）
│   ├── shipment/                   #   发运单（执行域主单：下发/拆分/拼单关联）
│   ├── waybill/                    #   运单（运输执行全生命周期，状态只前进 [ADR-013]）
│   ├── dispatch/                   #   调度派车（匹配车辆/承运商、排线）
│   ├── track/                      #   在途跟踪（节点回传、状态流转、超时预警任务）
│   ├── sign/                       #   签收（仅状态登记，附件后置）
│   └── report/                     #   TMS 报表（预聚合表 rms? → 统一 tms_rpt_* 命名，单库阶段直查聚合）
│
│   # （tms-wms / tms-fee 不建——WMS/结算为外部系统，不在本项目建设范围）
│
└── tms-admin/                      # 【启动】Spring Boot 入口，聚合以上模块依赖 + application-{env}.yml
```

> 最初写作 `tms-tms` 时语感重复、且会产出 `com.tms.tms.shipment` 这样的包路径；
> 趁批 0 尚未沉淀业务代码时改掉，代价仅为改 `pom.xml` 与三个包名。服务边界不变，只是命名——

## 3. 跨模块调用规则（报告 5.2 五条，一字不改执行 + 一条补充）

1. 只能调用其他模块的 **Service 接口**，禁止注入对方 Mapper / 直接访问对方数据库。
2. 其他模块只能依赖接口，不能依赖实现类。
3. 跨模块禁止直接操作对方表，必须走对方 Service。
4. 跨模块传输用 **DTO**，禁止外传 Entity。
5. 每张表加模块前缀（sys_/base_/tms_）。
6. （补充 A-3）接口与 DTO 集中在模块 `api/` 子包——阶段 2 拆服务时把 `api/` 提成独立 jar、Feign 实现同名接口，调用方代码零改动。配合 ArchUnit 测试把 1–4 条固化成 CI 红线（报告第八章风险首条的应对）。

## 4. 数据库规范（报告 7.1–7.3 为基线）

- **表命名**：前缀制。TMS 核心表示例：`tms_order`、`tms_order_item`、`tms_dispatch`、`tms_track_event`、`tms_receipt`、`tms_fee_record`、`tms_rpt_*`（报表聚合）。
- **必含字段**（每张表，报告 7.2）：`id`（**号段模式**，应用层发号——分库不冲突，2026-10-04 决议）、`tenant_id`（预留字段，拦截器暂不启用）、`created_by/created_at/updated_by/updated_at`、`version`（乐观锁）、`deleted`（逻辑删除 0/1）。
  > `[已决策 2026-10-04：批 0 实装修正]` 审计字段原名写作 `create_by/create_time/update_by/update_time`，实装时统一改为
  > `created_by/created_at/updated_by/updated_at`：与事件信封的 `occurred_at` 同风格，且 `_at` 后缀一眼区分"时间点"与"时间长度"。
  > 落点：`BaseEntity` + `AuditMetaObjectHandler`，各业务表无需重复声明。
  > **事实表不适用**：发件箱/收件箱等表只有 `created_at`，没有 `updated_*`/`deleted`/`version`——事件发出去不能"改"，只能置 DEAD 等人工处理。
- 唯一键一律含 `tenant_id`（租户内唯一语义）。
- **索引先行**：列表页查询模式第一天设计复合索引；报表走预聚合表；运单类大表第一天定归档策略（01 报告对老系统的教训，属通用工程原则，采纳）。
- 分库映射（拆服务时按前缀平移）：auth_db←sys_ / base_db←base_ / tms_db←tms_。
- 补充两张横切表（02 AI-ready 原则 1/3，MVP 即落）：
  - `tms_event`：单据节点事件时间线（对象类型、事件、时间、操作人、位置）——状态流转的真相源，未来 ETA 预测/问数助手的数据底座，避免"只存当前状态字段"。
  - `sys_attachment`：附件元数据（业务类型、关联单据、存储 key、上传人），文件本体在对象存储。
- 借鉴项（非基线）：若业务范围包含承运商/司机等外部参与方，其跨工厂可见性可参照 [03](references/03-权限管理统一设计方案.md)/[04](references/04-核心单据字段清单.md) 的参与方列（carrier_org_id 等）方案——那是另一系统验证过的思路，本系统按实际范围取舍。

## 5. 认证与权限（按报告口径，不预设复杂度）

- 单体阶段：Spring Security + JWT，auth 模块管用户/角色/菜单/按钮权限 + 操作日志；Token 校验过滤器进程内生效；会话态数据放 Redis（无状态可水平扩，报告第 3 章）。
- `tenant_id` 注入：登录时选定/默认生效工厂，框架拦截器统一过滤（§4）。
- 阶段 2 拆出认证服务后：各服务以 JWT 校验 + Gateway 统一鉴权，认证服务即报告所称"第一个拆的服务"。
- RBAC 之上是否需要组织树数据权限（本部门/及以下等档位）：属 [03] 参考方案内容，待本系统业务范围确认后决策，MVP 不做。

## 6. 初始建设范围（TMS 为主）

**做**：auth + base（工厂/客户/供应商/地点/车辆/司机/商品/字典）+ tms 全链路（订单→调度派车→在途跟踪→签收→TMS 报表）+ framework 横切组件 + tms-web + 司机小程序（uni-app）。计费不在范围（ADR-017）。

**不做**（触发条件明确，防范围蔓延）：WMS/结算（外部系统，不在建设范围）、微服务组件（阶段 2）、MQ（单体+定时任务够用，出现削峰/解耦需求再评估轻量方案）、细粒度拆分（报告第二章已否决）。

第 0 步交付：全部模块空壳 + framework（**号段发号**/审计/租户拦截器/事件框架）+ tms-admin 可启动 + CI（含 ArchUnit 边界测试），一周内完成，之后按域逐个实装。依赖坐标与版本按 [13](13-gate0-技术栈验证报告.md) §2 锁定矩阵。
