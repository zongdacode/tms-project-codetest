## 1. 架构总览

**Spring Boot 单体（1 应用 + 1 库）；不做微服务拆分，只保留一条模块边界。**（[ADR-018]，2026-10-05）

技术栈（报告第六章，版本修正见 §8-A1）：

| 层 | 选型 |
|---|---|
| 后端 | JDK 21 LTS + **Spring Boot 4.1.1**（Gate 0 已过，见 [13](13-gate0-技术栈验证报告.md)）+ MyBatis-Plus **3.5.17**（boot4 starter）+ Spring Security/JWT + SpringDoc **3.1.1** |
| 数据 | MySQL 8.4：单库分表前缀 → 拆服务时按前缀分库 + Redis 7.x（缓存/Token/分布式锁）+ 对象存储（附件/回单） |
| 服务化 | **不做**（[ADR-018]）。仅当计划表迁出为订单中心（[ADR-015]）确实需要独立部署时，才在该边界上引入远程调用；届时候选 Spring Cloud Alibaba（Nacos/Gateway/OpenFeign） |
| 前端 | Vue 3 + TypeScript 5 + Element Plus + Vite + Pinia + Vue Router + Axios |

```
            Web 前端 (tms-web)
                 │ HTTPS
       [ tms-admin 单体应用 ] ◄── 外部系统对接（随 TMS 业务范围确定）
                 ▼
   tms-core（唯一业务模块：auth/base + 执行各域）  │  tms-plan（计划表）
        两者之间只走 com.tms.plan.api，禁止跨模块查表
                 ▼
  MySQL 单库（sys_/base_/tms_ 前缀） + Redis + 对象存储
```

演进节奏（报告第四章，TMS 起步下做范围收紧；2026-10-05 取消服务化阶段）：

| 阶段 | 形态 | 触发 |
|---|---|---|
| 1（当前，且是常态） | 单体：tms-core 各域实装 + tms-plan；tenant_id 多工厂隔离 | 第 1–3 个月起 |
| 未来演进（唯一预留） | 计划表整体迁出为订单中心（[ADR-015]/[09]） | 触发条件见 [09] §1，尚未成立 |

> **不再有阶段 2/阶段 3。** 报告原设想的"拆统一认证服务（Nacos/Gateway/Feign）""基础数据独立"
> 已取消：认证与基础资料并入 tms-core 作为普通域，没有跨进程调用的必要，
> 引入注册中心/网关只会把进程内调用变成分布式事务。依据 [ADR-018]。

## 3. 模块边界规则（只约束 `tms-plan` ↔ `tms-core`）

报告 5.2 给了五条"跨模块只调接口"的规则。**2026-10-05 收拢后，它们只适用于一条边界**：
`tms-plan` 与 `tms-core` 之间。`tms-core` 内部各域（auth / base / shipment / waybill / …）
同属一个模块、同一次部署、同一个本地事务，**直接互相调用即可，不需要任何接口层**（[ADR-018]）。

适用于 plan ↔ core 的规则：

1. 只能调用对方的 **Service 接口**，禁止注入对方 Mapper / 直接访问对方数据库。
2. 只能依赖接口，不能依赖实现类。
3. 禁止直接操作对方表，必须走对方 Service。
4. 跨界传输用 **DTO**，禁止外传 Entity。
5. 接口与 DTO 集中在 `tms-plan/src/main/java/com/tms/plan/api/`——计划表迁出为订单中心时，
   把这一个包换成远程实现，`tms-core` 一侧代码零改动。这是它作为**唯一保留边界**的全部价值。

**全库通用（与模块边界无关）**：每张表加域前缀（`sys_` / `base_` / `tms_`）。
这不再是"模块边界"的体现，而是**数据按域归类**的约定——同库共存，便于查数、审计与将来按域归档。

> 规则 1–4 由 ArchUnit 测试固化为 CI 红线（[10] R-1，实现见 `ArchRules.planAndExecutionMustNotShareInternals`）。
> 原第 6 条（"每个业务模块都开 api/ 子包"，即 A-3）已删除——收拢后它与 R-1 语义完全重合。

## 4. 数据库规范（报告 7.1–7.3 为基线）

- **表命名**：前缀制。TMS 核心表示例：`tms_order`、`tms_order_item`、`tms_dispatch`、`tms_track_event`、`tms_receipt`、`tms_fee_record`、`tms_rpt_*`（报表聚合）。
- **必含字段**（每张表，报告 7.2）：`id`（**号段模式**，应用层发号——分库不冲突，2026-10-04 决议）、`tenant_id`（预留字段，拦截器暂不启用）、`created_by/created_at/updated_by/updated_at`、`version`（乐观锁）、`deleted`（逻辑删除 0/1）。
  > `[已决策 2026-10-04：批 0 实装修正]` 审计字段原名写作 `create_by/create_time/update_by/update_time`，实装时统一改为
  > `created_by/created_at/updated_by/updated_at`：与事件信封的 `occurred_at` 同风格，且 `_at` 后缀一眼区分"时间点"与"时间长度"。
  > 落点：`BaseEntity` + `AuditMetaObjectHandler`，各业务表无需重复声明。
  > **事实表不适用**：发件箱/收件箱等表只有 `created_at`，没有 `updated_*`/`deleted`/`version`——事件发出去不能"改"，只能置 DEAD 等人工处理。
- 唯一键一律含 `tenant_id`（租户内唯一语义）。
- **索引先行**：列表页查询模式第一天设计复合索引；报表走预聚合表；运单类大表第一天定归档策略（01 报告对老系统的教训，属通用工程原则，采纳）。
- 分库映射：**不拆库**。`sys_` / `base_` / `tms_` 三组前缀同库共存，仅按域归类；若将来某个域确实要独立部署（如计划表迁出），再按前缀平移。
- 补充两张横切表（02 AI-ready 原则 1/3，MVP 即落）：
  - `tms_event`：单据节点事件时间线（对象类型、事件、时间、操作人、位置）——状态流转的真相源，未来 ETA 预测/问数助手的数据底座，避免"只存当前状态字段"。
  - `sys_attachment`：附件元数据（业务类型、关联单据、存储 key、上传人），文件本体在对象存储。
- 借鉴项（非基线）：若业务范围包含承运商/司机等外部参与方，其跨工厂可见性可参照 [03-权限管理统一设计方案](03-权限管理统一设计方案.md)/[04](references/04-核心单据字段清单.md) 的参与方列（carrier_org_id 等）方案，本系统按实际范围取舍。

## 5. 认证与权限（按报告口径，不预设复杂度）

- 认证与权限由 `tms-core` 的 **auth 域**承担：Spring Security + JWT，用户/角色/菜单/按钮权限 + 操作日志；Token 校验过滤器进程内生效；会话态数据放 Redis（无状态可水平扩，报告第 3 章）。
- **不拆认证服务**（[ADR-018]）：进程内校验，不经 Gateway。
- `tenant_id` 注入：登录时选定/默认生效工厂，框架拦截器统一过滤（§4）。
- 权限模型的设计依据是 [03-权限管理统一设计方案](03-权限管理统一设计方案.md)（2026-10-05 起为本系统核心文件）。
- RBAC 之上是否需要组织树数据权限（本部门/及以下等档位）：MVP 不做，需要时从 [03](03-权限管理统一设计方案.md) 取用。

## 6. 初始建设范围（TMS 为主）

**做**：`tms-core` 全链路（auth 用户/角色/权限 + base 基础资料 + 订单→调度派车→在途跟踪→签收→TMS 报表）+ `tms-plan` 计划表 + framework 横切组件 + tms-web + 司机小程序（uni-app）。计费不在范围（ADR-017）。

**不做**（触发条件明确，防范围蔓延）：WMS/结算（外部系统，不在建设范围）、微服务组件（已取消，[ADR-018]）、MQ（单体+定时任务够用，出现削峰/解耦需求再评估轻量方案）、细粒度拆分（报告第二章已否决）。

第 0 步交付：5 个模块空壳 + framework（**号段发号**/审计/租户拦截器/事件框架）+ tms-admin 可启动 + CI（含 ArchUnit 边界测试），一周内完成，之后按域逐个实装。依赖坐标与版本按 [13](13-gate0-技术栈验证报告.md) §2 锁定矩阵。
