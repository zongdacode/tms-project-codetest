## 1. 文档定位

| 项 | 内容 |
|---|---|
| 甲方 | SH控股集团（四大业务板块：汽零、先途电子、微通道、家用/商用） |
| 实施方/原厂 | 青岛家哇云网络科技有限公司（第三方 SaaS 供应商） |
| 项目 | **OTWB 平台** = OMS(订单) + TMS(运输) + WMS(仓储) + BMS(账单) + RMS(报表) |
| 业务范围 | 国内发运 + 国外发运国内段；成品物流；正向/逆向/横向三类场景 |

## 2. 系统全景

### 2.1 端与模块清单

| 端 | 模块 | 内容 |
|---|---|---|
| CMP 配置管理端 | 系统管理 | 账套、用户、角色（按钮级权限+数据权限4档）、部门、职位、数据字典、菜单、操作/登录日志 |
| MDM 基础数据端 | 基础数据 | 承运商、线路（含时效）、车辆、司机、**承运商价格体系**、客户（含电子围栏）、物料（含包装绑定）、包装、托盘、集装箱、港口、车型、仓库（含月台） |
| OMS 订单管理端 | 订单 | 异常订单（上游脏数据修正）、物流订单（确认/拆改/跟踪）、订单拼车（拼车池） |
| TMS 运输管理端 | 运输 | 运单（匹配承运商+自动计费）、智能配载（组托+装箱方案）、临时议价（在线竞价）、任务单（提货/干线/中转/配送）、车辆监控（实时定位+轨迹）、异常管理、运输时效预警、回单管理 |
| WMS 仓储管理端（薄） | 园区 | 园区车控（月台预约/到厂时间/装车确认）、库存查询（转发 PES 查询） |
| BMS 账单管理端 | 结算 | 费用调整、费用调整审核、对账单管理（确认/审核/发票/结算）、外仓费用、降本/超额运费统计 |
| RMS 报表管理端 | 报表 | 12 张统计报表 + 物流数字仪表盘 |
| 承运商 PC 端 | 独立账套 | 自有组织/用户/车辆/司机管理 + 接单、提货、派车、签收、打印送货单、报价 |
| 司机微信小程序 | 移动 | 任务列表、提货确认、签收/异常签收、转车（含转车码）、回单上传、历史/异常记录 |
| 客户微信小程序 | 移动 | 运单查询、任务明细、签收/异常签收、历史运单 |
| 外务（销售）小程序 | 移动 | 物流订单查询、节点跟踪、车辆位置 |

### 2.2 核心单据链路（系统主干）

```
发货计划（PES/MES/SAP/报表平台 经ESB推送）
  → 异常订单修正（OMS）
  → 物流订单（确认、补全地址、可选拼车）
  → 运单（自动匹配承运商+计费；或临时议价后生成）
  → 任务单-提货（承运商派车 → 司机到厂 → 仓库看板/月台 → 装车确认→重算运费→打印送货单）
  → 任务单-干线/中转/配送（节点跟踪：北斗定位 + 司机小程序）
  → 签收（客户/司机/承运商端，上传回单）
  → 回单回收/审核
  → 费用生成（按价格体系自动计算，支持调整+审核）
  → 对账单（承运商线上确认 → 内部审核 → 发票 → 结算）
```

## 3. 核心业务复杂度排序（决定重写工作量）

1. **计费引擎**（最复杂、最核心）：4 类计费模型（零担按体积/重量 + 整车按车型×车数 + 快递按重量区间 + 海运按箱型）× 15+ 费用项（运费、取/送货费、卸货费、订舱费、THC、报关费、拖卡费、待时费、超远配送费、油价费、托盘返回费、木架费、上楼费、空车费、其他1/2）× 重泡比折算 × 最低收费（取/送）× 含税/不含税换算 × 临时议价 × 整车/零担差额记录（降本/超额）× 装车数量变动重算。
2. **多租户与权限**：账套隔离（企业=系统/承运商两类）；四大业务板块数据互不可见；数据权限 4 档（所有/自定义/本部门/本部门及以下）；按钮级功能权限。
3. **单据状态体系**：运单有 6 个平行的三态状态维度（分配/提货/干线/中转/配送/签收，各为未/部分/已）+ 任务单 8 状态 + 异常与预警状态。**PRD 未给出完整状态机与逆向流转规则**（取消派车、追加订单到已派车运单等散落各处）。
4. **上游集成**：四大板块四个来源（PES 发货计划/打包看板、MES 发货计划、SAP 交货单、微通道报表平台），且要处理缺货少发同步、超发禁止（源头修改）、修改联动（已生成运单/已派车时的处理链）。
5. **智能配载**：组托方案（包装-托盘堆码规则）+ 集装箱/车辆装载方案（重心、限重、重不压轻），输出装载图与利用率。本质是 3D 装箱算法，PRD 只有输入输出定义。
6. **在途跟踪**：中交兴路（≥9.6米车）+ 司机小程序定位（<9.6米/危化品车）双通道 + 电子围栏（客户地址/仓库自动判定到车）。
7. **拼车池**：跨业务板块同线路+同时效拼车，双方确认后任一方建运单。

## 4. PRD 成熟度评估（作为 AI 重写的输入）

### 4.1 可直接使用 ✅

- **功能清单到字段/按钮级**：每个模块都有"关键字段/首页表单字段/查询条件"清单 → 可直接转化为 backlog、API 定义和表单结构。
- **as-is 现状流程非常详尽**：四大板块各自的订单获取、发运计划、拣货打包、匹配承运商、对账流程逐板块描述 → 业务规则的第一手材料。
- **计费维度基本齐全**：价格体系章节（MDM）+ 费用计算逻辑章节（TMS）合起来覆盖了主要计费场景。
- **30+ 张页面截图**：作为 UI 布局参考。
- **术语定义清晰**：发货需求/送货单/物流订单/运单有明确定义。

### 4.2 缺失与矛盾（按风险排序）

**P0 — 不补齐就没法开工或必然返工：**

1. **接口规范全部缺失**。ESB 报文格式、字段映射、调用频率、失败重试/补偿机制，全文只有一句"通过 ESB 对接"。OMS 的数据来源全靠这些接口，这是重写的最大单点风险。→ 需要向家哇云/ESB 团队索取接口文档，或抓包/日志反推。
2. **没有数据模型**。无 ER 图、无数据字典；同一实体的字段在不同章节不一致（运单费用项在 TMS/BMS/承运商端三处列举有出入：空车费、木架费、上楼费时有时无）。→ 需要在设计阶段统一重建。
3. **非功能需求为零**。无年运单量、日均峰值、并发用户数、性能/可用性指标。→ 无法针对性设计索引、分表、归档策略，也就无法保证"不重蹈慢查询覆辙"。**必须由用户提供。**

**P1 — 开发中会频繁碰到：**

4. 状态机联动规则不完整：状态枚举有了，但流转触发条件、并发冲突（承运商派车 vs 物流改单）、逆向流转只部分描述。
5. 计费公式歧义：零担"体积×单价"与"重量区间单价"并存；重泡比无折算公式；卸货费"XX元/件"与"按箱子数量"口径不一。
6. 权限矩阵没有默认角色清单（有权限模型，没给每个业务角色该配什么权限）。
7. 报表口径不精确：12 张报表只有查询字段，及时率的分子/分母、超时判定规则无定义。

**P2 — 可后期补充：**

8. 配载算法只有输入输出定义（需单独的算法设计）。
9. 通知清单散落（短信/公众号/邮件散见各节，无统一汇总）。
10. WMS 库存查询的需求本身未确认（文中写"需要业务部门向 PES 提出"）。

## 5. 老系统技术栈与重写技术判断

### 5.1 老系统（据 PRD 第5章 + 架构图）

- Spring Cloud Alibaba（Hoxton）+ Spring Boot 2.3 + Nacos + Sentinel + Gateway + OpenFeign + MyBatis-Plus + sa-token + xxl-job
- **oms/tms/bms 三服务三库**（MySQL 8 分库）+ MongoDB + Elasticsearch + Kafka + Redis + OSS，k8s 部署
- 前端 Vue 2.6 + Element UI 2.14

### 5.2 判断

- 2023 年的选型放到 2026 年已过时：Vue 2、Spring Boot 2.3 均已 EOL，fastjson 1.x 有漏洞史。
- **对这个体量，微服务+分库+Kafka+ES 全家桶偏重**。企业内部物流平台（用户=内部员工+承运商，并发有限）承担了分布式事务、最终一致性、跨库 join 的全部成本——这很可能就是原系统复杂难治、慢查询丛生的结构性原因之一。
- **重写建议：模块化单体（modular monolith）起步**。单服务+清晰的模块边界（cmp/mdm/oms/tms/bms/rms 一个数据库内按 schema/模块隔离），保留未来按模块拆出的能力。理由：性能问题在单体里可观测、可诊断；AI 辅助开发与维护的成本大幅降低；团队无需运维分布式全家桶。
- 无论选什么栈，**数据库设计是 TMS 的命根子**：列表页查询模式先行设计索引、报表走预聚合/汇总表、运单大表第一天就定归档策略。
- 状态模型建议重新设计：**运单主状态机 + 节点事件时间线表**，取代 6 个平行状态字段的组合爆炸。
- 多租户/账套模型必须保留——这是业务本质需求，不是技术包袱。

## 6. 范围策略建议（不必 1:1 复刻）

| 阶段 | 内容 | 理由 |
|---|---|---|
| MVP（业务闭环） | MDM 核心主数据（承运商/线路/价格体系/客户/物料/仓库）+ OMS 物流订单 + TMS 运单/任务单 + 装车/签收/回单 + BMS 费用/对账 + 承运商 PC 端 + 司机小程序 | 跑通"订单→运输→签收→结算"主干，业务才能切过来 |
| 二期 | 拼车池、临时议价、时效预警、异常管理、客户/外务小程序、12 张报表 | 依赖主干数据积累 |
| 评估后决定 | 智能配载算法（可先用简化估算：按托/箱数估箱量）、园区车控、数字仪表盘、快递100 轨迹、WMS 库存查询 | 算法重、依赖外部、需求未确认 |
